## 案例一：从学生账号到6000+教师身份证信息泄露

**来源：** 先知社区（xz.aliyun.com/news/19045）/ 腾讯云开发者社区  
**时间：** 2024年  
**漏洞类型：** 信息泄露（IDOR越权）

### 1. 目标是什么

某某学院一站式服务大厅——典型的edu"大而全"门户系统。

### 2. 为什么选这个目标

"edu系统一直是很好的练手场景，系统多、类型丰富，也经常能碰到一些意想不到的安全问题。"  
而且edu系统通常WAF配置不严，前后端分离架构给了很多测试机会。

### 3. 具体步骤

**第一步：登录后信息观察**  
不急于操作，先观察门户设计和信息暴露情况。发现系统集成子模块众多，数据在不同模块间流转。

**第二步：开启Burp Suite监听**  
正常点击各个功能模块，观察后台API调用。"不要用任何扫描器，就是正常用户操作。"

**第三步：发现可疑接口**  
注意到了一个 `getUserInfo` 类的API接口，返回了大量用户信息字段。

**第四步：IDOR漏洞验证**  
修改请求中的 `userid` 参数，换成其他数字——系统直接返回了该用户完整信息，包含身份证号。

**第五步：扩大收集面**  
在在线课程/直播选课页面，意外发现该页面直接展示了所有教师的详细信息（含userid）。  
"edu系统经常会在各种功能页面无意中暴露用户ID信息，这些信息与越权漏洞结合，威力会成倍放大。"

**第六步：批量验证**  
用收集到的userid逐个查询，确认可以获取6000+教师的完整身份证信息。

### 4. 思维过程

"前端需要什么数据，后端API就会返回什么，而且往往为了开发方便，会返回比前端实际需要更多的字段。"  
开发商更关心功能实现，权限控制粗糙。一站式门户整合多个子系统，API设计"开放"——这就给了IDOR机会。

### 5. 确认方式

手工修改请求参数，连续验证多个不同userid均能获取数据。截图保存了多组验证结果。

### 6. 漏洞价值

eduSRC高危漏洞，直接导致批量教师敏感信息泄露。估分：**高危，多个严重级别**。

### 学到的核心经验

> "这个攻击过程其实很简单，没用什么高深技术。关键在于两个点：一是发现了不做权限检查的API接口，二是找到了大量目标用户ID。两个信息一结合，就变成了批量敏感数据泄露。"

## 案例二：某大学就业系统 SQL 注入

**来源：** 先知社区（xz.aliyun.com/news/19045）  
**时间：** 2024年  
**漏洞类型：** SQL注入

### 1. 目标是什么

某大学学生就业综合管理服务平台。

### 2. 为什么选这个目标

就业系统的统计功能通常比较复杂，需要根据不同条件进行数据筛选和汇总。"开发者为了实现灵活的查询，可能会动态构造SQL语句，这就为SQL注入创造了条件。"

### 3. 具体步骤

**第一步：进入个人中心，观察功能**  
重点关注统计类功能模块。

**第二步：发现页面跳转异常**  
操作过程中页面出现错误提示。"当页面出现异常或错误提示时，往往意味着后台处理出现了问题。这种情况下要及时进行抓包分析。"

**第三步：Burp Suite分析请求**  
通过抓包发现一个复杂的POST请求，包含多个参数。"不是每个参数都存在注入。要根据参数名称和功能推测其用途，优先测试那些明显用于数据查询的参数，如id、name、type等。"

**第四步：确认注入点**  
在某个参数中测试单引号，返回了数据库错误信息。

**第五步：sqlmap获取交互式SQL shell**  
```
sqlmap -u "目标URL" --data "参数=值" --dbs
```
成功获取数据库控制权。

### 4. 思维过程

"统计类功能经常需要根据用户输入构造复杂的SQL查询"——这是功能本身的特性决定的。复杂的POST请求要优先关注数据查询参数。

### 5. 确认方式

通过sqlmap获取了交互式SQL shell，确认能查询数据库内容。

### 6. 漏洞价值

eduSRC高危SQL注入。估分：**高危，300-800元**（edu通用类）

### 学到的核心经验

> "复杂的POST请求往往包含多个参数，不是每个参数都存在注入。要根据参数名称和功能推测其用途，优先测试那些明显用于数据查询的参数。"

## 案例三：参数绕过 → 越权 → 任意文件下载的链条

**来源：** 先知社区（xz.aliyun.com/news/19045）  
**时间：** 2024年  
**漏洞类型：** 逻辑缺陷 + 越权访问 + 任意文件下载（组合拳）

### 1. 目标是什么

某edu系统。

### 2. 为什么选这个目标

edu系统多入口设计，不同入口安全检测标准可能不一致。

### 3. 具体步骤

**第一步：测试登录**  
发现URL中的参数 `-1`，尝试改为 `1`——成功绕过了权限验证（虽然被踢出了登录）。

**第二步：被踢出但获得有用信息**  
虽然被踢出登录，但在过程中拿到了管理员路径 `/admin/xxxxx.html`。  
"即使被系统踢出，但获得的路径信息仍然有价值。"

**第三步：发现专家通道**  
edu系统通常有多个入口：学生、教师、管理员、专家等。尝试使用"专家通道"——这入口的安全检测较弱。

**第四步：路径拼接越权**  
将管理员路径拼接到当前URL下：
```
当前URL/../admin/xxxxx.html
```
成功访问了账号管理功能！

**第五步：添加管理员账号**  
利用越权功能创建一个新的管理员账号。

**第六步：修改管理员密码**  
无身份校验限制，直接修改了新管理员的密码，获得完整权限。

**第七步：发现任意文件下载**  
在"大数据管理"模块的"下载模板"功能中，发现下载路径可以由用户控制。

**第八步：抓包分析下载请求参数**  
用Burp Suite抓取下载请求，分析参数结构。原始参数：
```json
{"excel":"xxxxDataTemplate","id":"正常的模板文件名"}
```
修改为：
```json
{"excel":"xxxxDataTemplate","id":"../web.config"}
```
成功下载了web.config配置文件。

### 4. 思维过程

"这种简单的参数修改绕过验证在edu系统中很常见。开发者可能使用简单的数字标识来区分不同的权限级别，但没有在服务端进行严格的权限校验。"  
"路径拼接是一种常用的越权测试方法。当发现某个功能路径后，可以尝试将其与不同的base URL组合。"

### 5. 确认方式

先创建管理员账号并登录，确认获得了管理权限。然后通过修改下载参数成功读取到web.config配置文件。

### 6. 漏洞价值

组合漏洞链：逻辑缺陷(中危) + 越权(高危) + 任意文件下载(高危)。**估分：高危-严重，500-1500元**

### 学到的核心经验

> "edu系统经常会设置多个访问入口（学生、教师、管理员、专家等），不同入口的安全检测标准可能不一致。测试时要尝试发现和利用这些不同的访问通道。"

## 案例四：找回密码响应包修改 → 任意密码重置

**来源：** 先知社区 / 火山引擎开发者社区  
**时间：** 2024年  
**漏洞类型：** 逻辑漏洞（响应包篡改）

### 1. 目标是什么

某企业后台管理系统。

### 2. 为什么选这个目标

"开局一个登录框"——弱口令测试无果后，把注意力转向找回密码功能。登录框最常见，也最容易出现逻辑漏洞。

### 3. 具体步骤

**第一步：测试找回密码**  
输入两个非法参数，点击获取验证码。抓包查看响应，发现返回 `errorCode: 0`（前端显示"未查询到账户信息"）。

**第二步：修改响应包**  
再次抓包，将响应包中的 `0` 改为 `1`，放包后成功进入第二步。  
前端自动请求了一个后端接口发送验证码。

**第三步：验证码泄露**  
查看发送验证码接口的响应——**验证码以明文形式被返回在响应体中**！

**第四步：填入验证码进入修改密码页**  
提交新密码时，发现请求体中只有 `userIds` 和 `password` 两个参数。"猜测这里可能存在任意账户密码重置。"

**第五步：尝试修改管理员密码**  
意识到传入的用户不存在（userid为0），于是将 `userIds` 字段改为 `1`。后端响应为 `1`——密码重置成功！  
但用新密码登录管理员失败——原来管理员uid不是1。

**第六步：APP反编译获取信息**  
注意到有APP下载二维码，下载apk后用 `AppInfoScanner` 快速扫描：
```bash
https://github.com/kelvinBen/AppInfoScanner
```
发现两个移动端接口地址。

**第七步：未授权接口泄露所有用户信息**  
访问发现的新接口——好家伙，返回了所有用户的uid和电话号码！彻底贴脸。

**第八步：找到管理员uid**  
通过泄露的接口找到真正管理员的uid，确认了漏洞链的完整性。出于安全考虑，只重置了一个普通用户密码做验证。

### 4. 思维过程

"弱口令无果后注意力转到找回密码处"——这是标准测试流程。关键转折在于两点：  
1. 发现验证码在响应包里明文返回  
2. 重置密码接口没有校验当前用户身份，仅靠前端传入的userid

### 5. 确认方式

成功重置了一个普通用户的密码并登录，验证了整个漏洞链条的可行性。同时确认了未授权接口泄露所有用户信息的严重性。

### 6. 漏洞价值

逻辑漏洞（密码重置缺陷） + 信息泄露（未授权接口）。**估分：高危-严重，500-2000元**

### 学到的核心经验

> "此路不通另寻他路"——登录框不行就找密码重置，Web不行就去看APP。多一个入口多一条命。

## 案例五：验证码与密码分包验证 → 登录绕过

**来源：** 博客园（BMCel） / 某SRC平台  
**时间：** 2024年5月  
**漏洞类型：** 登录绕过（响应包修改）

### 1. 目标是什么

某SRC资产收集过程中发现的登录页面。

### 2. 为什么选这个目标

在资产收集中发现登录页面，决定测试登录绕过。"通过抓包发现验证码和用户名密码是分包验证"——这是一个关键发现。

### 3. 具体步骤

**第一步：发现分包验证机制**  
先输入正确验证码和任意账号密码，抓包观察。发现验证码验证和用户名密码验证是**分开的HTTP请求**。

**第二步：拦截验证码验证的响应包**  
将第一步验证码验证的请求拦截，修改响应包：
```json
{
  "errorCode": "00000",
  "errorMsg": "成功",
  "data": true,
  "extra": null
}
```
保持 `data: true`，放包后系统认为验证码验证通过。

**第三步：直接进入登录后续流程**  
验证码绕过成功后，后续的账号密码验证也被跳过了（或同样存在类似的响应判断），成功登录系统。

### 4. 思维过程

"分包验证"四个字就是关键——验证码验证是独立的请求，前端只根据响应中的 `data: true/false` 判断是否通过。那只要拦截响应包篡改返回结果即可。

### 5. 确认方式

修改响应包后成功登录到系统后台，看到工作台页面。

### 6. 漏洞价值

**中危-高危**。实际可登录系统，如果系统中有敏感数据则风险提升。**估分：200-800元**

### 学到的核心经验

> "响应包修改"是SRC中最容易上手也最常被忽视的漏洞类型。关键点：找分包验证、找只靠前端判断的操作。

## 案例六：小程序四个漏洞一锅端

**来源：** 腾讯云开发者社区（云+社区）/ Timeline Sec  
**时间：** 2024年  
**漏洞类型：** 逻辑漏洞 + 前端绕过登录 + 越权 + 信息泄露（四合一）

### 1. 目标是什么

补天公益SRC某公司的小程序资产。

### 2. 为什么选这个目标

"因为公益SRC很多时候拼手速和资产收集，所以这次直接瞄准小程序开搞。"  
小程序是SRC最容易出洞的方向之一——开发周期短、安全测试不充分。

### 3. 具体步骤

#### 漏洞一：逻辑漏洞导致信息泄露

**第一步：** 微信登录小程序，在"首页"点击"签收凭证"，抓取数据包。

**第二步：** 将数据包中的 `phone` 和 `mobilePhone` 参数置为空值。  
发现返回数据中仍然包含订单信息、手机号、姓名等敏感信息。

**第三步：** 访问返回数据中的 `fileUrlList` 参数对应的URL——发现全部是签收订单，包含手机号、姓名等敏感信息。

#### 漏洞二：前端绕过登录后台

**第一步：** 找到第二个小程序，是一个登录界面。随便输入账号密码并抓包。

**第二步：** 拦截响应包，将 `"code"` 修改为 `0`，两个 `false` 修改为 `true`。

**第三步：** 修改后成功登录，直接进入工作台。虽是未授权访问，但能拿到数据。

#### 漏洞三：越权漏洞

**第一步：** 找到第三个小程序，注册账号后在个人设置中心找到收货地址。

**第二步：** 抓取收货地址的数据包，发现存在 `member_id` 参数。

**第三步：** 修改 `member_id` 的值——越权成功，可以看到其他人的姓名、手机号、地址。

#### 漏洞四：信息泄露

**第四个小程序**最简单：直接贴脸开大，点开抓到一个数据包，响应包里直接包含用户敏感信息。

### 4. 思维过程

"小程序开发周期短，很多开发者会忽略安全测试。"  
做公益SRC讲究效率——直接怼小程序，方法就是正常的BP抓包 + 观察参数 + 修改参数。

### 5. 确认方式

截图保存每个漏洞的利用过程和返回数据。

### 6. 漏洞价值

四个漏洞打包提交，其中越权和信息泄露为高危。**总估分：600-2000元**

### 学到的核心经验

> 小程序测试三板斧：  
> 1. 响应包修改（改code、改true/false）  
> 2. 参数ID遍历（找到member_id/userid就改）  
> 3. 空参数测试（把参数置空看返回什么）

## 案例七：GitHub 信息泄露 → 拿下中危

**来源：** CSDN博客  
**时间：** 2024年  
**漏洞类型：** 信息泄露

### 1. 目标是什么

某厂商的代码仓库。

### 2. 为什么选这个目标

"利用github搜索语法寻找敏感信息"——这是最基础但最有效的信息收集手段。

### 3. 具体步骤

**第一步：确定目标**  
选定要测试的SRC厂商。

**第二步：GitHub搜索**  
使用GitHub搜索语法：
```
"目标厂商名" password
"目标厂商名" config
"目标厂商名" secret
"目标厂商名" db_password
```

**第三步：发现敏感信息**  
在搜索结果中找到了厂商某项目的配置文件，里面包含数据库连接信息。

**第四步：确认可用性**  
验证数据库连接信息仍然有效，确认敏感信息泄露。

### 4. 思维过程

"信息收集是漏洞挖掘中极其重要的一环。"  
很多厂商的开发者会把配置文件或者带有敏感信息的代码push到公开仓库。

### 5. 确认方式

使用泄露的连接信息成功连接数据库，验证有效性。

### 6. 漏洞价值

**中危**。因为只是敏感信息泄露，未造成进一步危害。**估分：100-300元**

### 学到的核心经验

> GitHub搜索语法是信息收集的必备技能。常用搜索词：password、secret、config、token、api_key、db_password、内网地址。

## 案例八：空参数测试 + APP反编译 → 全站用户信息泄露

**来源：** 火山引擎开发者社区（转载自先知社区）  
**时间：** 2024年  
**漏洞类型：** 信息泄露 + 逻辑漏洞（密码重置）

### 1. 目标是什么

某企业Web管理系统 + 配套APP。

### 2. 为什么选这个目标

登录框测了一圈没有发现漏洞，但"注意力转到找回密码处"——从登录口转向业务逻辑。

### 3. 具体步骤

**第一阶段：找回密码逻辑漏洞**

**第一步：** 输入非法参数 + 获取验证码 → 抓包发现返回 `code: 0`

**第二步：** 修改响应包 `0→1` → 前端认为验证通过 → 进入第二步

**第三步：** 前端自动请求发送验证码接口 → 验证码在响应中明文返回！

**第四步：** 填入验证码进入密码重置步骤 → 请求体只有 `userIds` + `password`

**第五步：** 将 `userIds` 从 `0` 改为 `1` → 后端返回成功 → 但登录失败（管理员不是uid=1）

**第二阶段：APP反编译**

**第六步：** 转战APP → 使用 `AppInfoScanner` 扫描APK →
```
https://github.com/kelvinBen/AppInfoScanner
```

**第七步：** 发现未授权接口 → 访问后返回了**所有用户的uid和电话号码**

**第八步：** 找到uid=?
的管理员 → 配合第一阶段的密码重置漏洞 = 组合拳

### 4. 思维过程

Web走不通就走APP，"此路不通另寻他路"。  
扫码二维码下载APK，反编译扫描新接口——用工具快速发现移动端特有的API端点。

### 5. 确认方式

通过未授权接口确认数据真实性，通过密码重置确认漏洞可利用性。

### 6. 漏洞价值

两个漏洞组合：信息泄露(高危) + 任意密码重置(高危)。**总估分：高危，500-2000元**

## 案例九：从404到RCE + 未授权的"逆袭"

**来源：** CSDN博客  
**时间：** 2024年初  
**漏洞类型：** 未授权访问 + 文件上传RCE

### 1. 目标是什么

某OA系统。

### 2. 为什么选这个目标

在探索过程中发现很多路径返回404，但"404页面往往隐藏着线索"。

### 3. 具体步骤

**第一步：大量扫描发现线索**  
使用目录扫描工具对目标进行扫描，虽然很多返回404，但通过分析404页面的特征发现了系统的指纹信息。

**第二步：确定系统类型**  
根据指纹信息确认目标使用的是某OA系统（CMS），开始查询该CMS的已知漏洞。

**第三步：发现未授权文件上传接口**  
找到该OA系统的一个文件上传接口 `uploadWxFile.do`，且该接口未做权限验证。

**第四步：构造上传请求**  
使用Burp Suite构造文件上传请求，上传webshell。

**第五步：连接webshell**  
成功上传后连接webshell，获得服务器控制权。

### 4. 思维过程

"404页面是宝藏"——很多系统在404页面会暴露版本号、框架信息等指纹。  
确定系统类型后，直接搜索该CMS的历史漏洞，比从头开始测试高效得多。

### 5. 确认方式

成功上传webshell并执行系统命令，确认已获得服务器权限。

### 6. 漏洞价值

**严重**。RCE+未授权组合。**估分：严重，1000-3000元**

### 学到的核心经验

> "不要被404吓跑"——404页面往往能告诉你系统的真实身份。确定CMS版本后查历史漏洞，有时能发现未修复的1day甚至0day。

## 案例十：某次SRC引起的连锁漏洞挖掘

**来源：** 长亭百川云  
**时间：** 2024年  
**漏洞类型：** 未授权访问 + SQL注入 + 文件上传（连锁）

### 1. 目标是什么

某企业的一套管理系统，包含Web端和小程序端。

### 2. 为什么选这个目标

从一次普通的SRC测试开始，发现了系列连锁反应。

### 3. 具体步骤

**第一步：发现未授权访问**  
在测试过程中发现某接口不需要登录即可访问，返回了大量敏感数据。

**第二步：顺着未授权接口发现SQL注入**  
在未授权接口的参数中测试SQL注入，发现其中某个参数存在注入点。

**第三步：利用SQL注入获取更多信息**  
使用sqlmap获取数据库中的管理员密码哈希值。

**第四步：万能密码 + 文件上传**  
通过获取的信息进入后台，发现上传功能，上传webshell。

**第五步：小程序端同样存在多个漏洞**  
测试关联小程序，发现多处越权和信息泄露。

### 4. 思维过程

"有时一个漏洞会引发连锁反应"——先找到入口点（未授权访问），然后在内部横向移动（SQL注入），最终拿到控制权（文件上传）。

### 5. 确认方式

完整走通从外部到内部的整个攻击链，每个环节都截图保存。

### 6. 漏洞价值

连锁漏洞打包提交。**总估分：严重，2000-5000元**

### 学到的核心经验

> 一个漏洞往往不是孤立的。未授权→SQL注入→文件上传，这是经典的攻击链。"连锁漏洞"的价值远大于单个漏洞之和。

## 案例十一：敏感三要素泄露 → 接管管理员

**来源：** 知乎专栏  
**时间：** 2025年  
**漏洞类型：** 信息泄露 + 逻辑漏洞

### 1. 目标是什么

某单位业务系统。

### 2. 为什么选这个目标

在资产收集阶段发现目标存在"敏感三要素"泄露——先做信息收集总是没错的。

### 3. 具体步骤

**第一步：信息收集阶段发现敏感信息**  
使用信息收集工具（fofa、Google hacking、GitHub）发现目标系统中存在明文存储的敏感信息。

**第二步：利用泄露信息进行登录**  
使用收集到的账号密码尝试登录成功。

**第三步：发现系统中更多漏洞**  
登录后发现系统存在多处逻辑缺陷，可以进一步提升权限。

**第四步：最终接管管理员账号**  
通过一系列逻辑漏洞组合最终获得了系统管理员权限。

### 4. 思维过程

"信息收集是渗透的第一步也是最重要的一步"——先收集，后利用。很多时候不需要什么复杂技术，泄露的信息本身就能打开大门。

### 5. 确认方式

手动验证登录、提权、最终获取管理员权限的完整流程。

### 6. 漏洞价值

**高危**。从信息泄露到完整接管。**估分：高危，500-1500元**

### 学到的核心经验

> 信息收集决定你能走多远。FOFA、GitHub、Google Hacking三件套是信息收集的基本功。  
> "敏感三要素"是指：账号密码、手机号、身份证号——泄露任何一个都可能引发连锁反应。

## 案例十二：EDUSRC 通用系统"捡漏"通杀

**来源：** 2024年SRC漏洞报告集  
**时间：** 2024年  
**漏洞类型：** 通用系统漏洞（信息泄露 + 越权）

### 1. 目标是什么

多个edu通用系统（多个学校使用的同一套系统）。

### 2. 为什么选这个目标

"通用系统"是最高性价比的挖洞方向——一套系统如果有漏洞，可以同时提交给使用该系统的所有学校。

### 3. 具体步骤

**第一步：识别通用系统**  
通过FOFA搜索特定指纹，发现多所学校使用同一款教务/管理系统。

**第二步：在一个系统上找到漏洞**  
挑选其中一所学校作为测试入口，按照标准流程测试，发现了一个信息泄露漏洞——未授权接口直接返回学生/教师个人信息。

**第三步：验证通用性**  
在另一所学校使用同一个接口测试，发现同样存在漏洞——确认是通用漏洞。

**第四步：批量提交**  
对该通用系统进行批量验证，最终上了近150分。

### 4. 思维过程

"通用系统的ROI最高"——一个洞能吃遍所有使用该系统的客户。  
关键是先用FOFA/鹰图等平台找大量使用同一系统的目标。

### 5. 确认方式

在多个独立部署的目标上验证漏洞均可复现。

### 6. 漏洞价值

**高危通杀**。一次提交覆盖多个目标。**总估分：高危，1000-5000+元**（取决于覆盖目标数量）

### 学到的核心经验

> "通用系统通杀是最爽的挖洞方式"——通过FOFA搜索同一指纹找到大量使用同一系统的目标，在一处找到漏洞后批量验证。

## 十四、从这些案例中总结的SRC挖洞黄金法则

### 法则一：信息收集决定一切

12个案例中，**至少8个**的起点是信息收集。不做信息收集就去挖洞，等于蒙眼走路。

**必做的信息收集清单：**
- [ ] FOFA/鹰图/360Quake查资产
- [ ] GitHub搜配置/密码/密钥
- [ ] Google/Bing Hacking搜敏感文件
- [ ] OneForAll/subfinder扫子域名
- [ ] 目录扫描（dirsearch/ffuf）
- [ ] 小程序资产盘点

### 法则二：响应包修改是最容易上手的技术

案例四、五、六、八都用了"修改响应包"这一招。  
原理很简单：**很多系统只在前端做判断，后端直接信任前端传来的结果。**

### 法则三：参数遍历是信息泄露的关键

案例一（userid遍历）、六（member_id遍历）都靠这个。  
只要在请求参数中发现类似 `id`、`uid`、`user_id`、`member_id` 的数字，就试着改改看。

### 法则四：多入口、多渠道、多维度

Web不行试APP（案例八）、网站不行试小程序（案例六）、主站不行试子站（案例十）。  
"此路不通另寻他路"——SRC挖洞的第一生存法则。

### 法则五：通用系统是提分捷径

案例十二告诉我们：找到一套多所高校共用的系统，一个漏洞可以反复提交。  
用FOFA搜索相同指纹的应用，一个洞吃遍天。

### 新手优先攻击方向（按出洞率排序）

1. **信息泄露** — 最简单，最常遇，最容易被忽视
2. **逻辑漏洞（越权/密码重置/响应包篡改）** — 不需要高深技术，全靠细心
3. **通用CMS/OA通杀** — ROI最高，一个洞吃一年
4. **SQL注入** — 经典题型，但需要一些SQL基础
5. **小程序测试** — 开发质量参差不齐，容易出洞
